# B113 — 渠道契约测试与模拟器

## 目标

为各渠道构建可版本化请求/响应、错误、超时、签名和 webhook 模拟。

## 前置条件

- 依赖批次：B112
- 读取 `policies/non-negotiables.md`、`architecture/REFERENCE_ARCHITECTURE.md`、`security/THREAT_MODEL.md`。
- 使用 `scripts/orchestrate.py status` 验证依赖证据真实通过，不得只依据文字声明。

## 实施要求

1. 把“为各渠道构建可版本化请求/响应、错误、超时、签名和 webhook 模拟。”转化为明确的领域接口、数据契约、错误语义和版本策略。
2. 实现代码与数据库变更时维持单向依赖、租户边界、审计和可回滚迁移。
3. 提供可重复的本地测试、CI 测试、故障注入和至少一个真实业务场景。
4. 测试环境不得使用生产凭证或真实卡数据；所有测试数据必须合成、脱敏或由官方沙箱提供。
5. 严重安全问题、账本不平、无法恢复或关键证据缺失时发布门禁必须阻断。

## 全局不可妥协控制

- 不得以客户端返回页、同步回跳或未验签通知作为支付成功依据；必须以已验证渠道事件或主动查询结果定责。
- 所有资金金额使用整数最小货币单位，禁止使用 binary floating point；币种精度来自受版本控制的货币元数据。
- 所有创建、确认、捕获、退款、回放和修复操作必须有幂等键、唯一约束、并发测试和审计事件。
- 敏感凭证不得出现在源码、日志、异常、追踪、数据库明文或 CI 制品；通过 KMS/HSM/Vault 短期解密。
- 业务订单由原项目拥有；支付平台只拥有支付事实、渠道交互、账本、对账和风控证据。
- 缺少测试、运行证据、追踪关系或安全证明时必须 fail closed，不得以人工口头确认代替。

## 自动化验证

- 正常路径、拒绝路径、超时路径和重复请求均有自动化测试。
- 验证日志和追踪不包含凭证、卡数据、完整支付令牌或不必要个人信息。
- 验证失败不会产生重复扣款、重复退款、重复履约或不可解释账本差异。
- 对验证器本身做负向测试，证明删除证据、伪造完成文件或跳过测试不会被判定为通过。

## 必交付产物

- 代码与配置变更
- 架构或契约文档
- 自动化测试结果
- 安全与运行证据
- traceability.json
- 发布门禁结果
- 独立复核记录

## 证据目录

- `evidence/B113/plan.md`
- `evidence/B113/commands.ndjson`
- `evidence/B113/test-results/`
- `evidence/B113/runtime/`
- `evidence/B113/security/`
- `evidence/B113/traceability.json`
- `evidence/completion/B113.json`

`completion/B113.json` 必须包含：批次 ID、状态 `passed`、提交 SHA、环境、开始/完成时间、执行者、测试摘要、安全摘要、产物哈希、依赖完成文件哈希和审查者。

## 完成门

只有以下条件全部成立才可标记通过：

1. 所有依赖批次的完成证据可验证且哈希一致。
2. 目标代码、迁移、配置、契约和文档已进入版本控制。
3. 正常、失败、重试、并发和安全测试全部通过；必要测试无跳过。
4. 不变量、租户隔离、审计、脱敏和回滚路径得到运行证明。
5. `traceability.json` 能从需求追踪到代码、测试、控制与证据。
6. 审查者不是该批次唯一实现者；关键资金与权限变更执行四眼复核。

任何条件不成立时，状态必须为 `blocked` 或 `failed`，不得使用“基本完成”绕过门禁。
