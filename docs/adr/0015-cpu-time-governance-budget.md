# ADR-0015: 治理门禁的预算改为进程 CPU 时间，挂钟只作兜底上限

- 状态：accepted
- 日期：2026-09-01
- 批次：B03
- 决策者：payment-platform-platform-eng payment-platform-architecture
- 关联需求：PAY-REQ-0049
- 关联控制：NN-12, CTRL-011, CTRL-018
- 取代：无

## 背景

`tools/paygov/repo.py` 的 `Budget` 从 B00 起就按**挂钟时间**计：每个验证器 30 秒，
超时抛 `BudgetExceeded`，CLI 转成 `VALIDATOR_ABORTED` 与退出码 3。当时这是对的——
它要防的是一个被恶意或损坏输入卡死的验证器把整条流水线挂住。

问题是这个门禁**不是 CPU 密集的，是 I/O 等待型的**。2026-09-01 在交付机上实测：

```
verify repo-hygiene --budget-seconds 600   4.62s user  1.31s system  25% cpu  23.298 total
verify-all                                 8.47s user  1.72s system  34% cpu  29.703 total
```

`repo-hygiene` 干了 **5.9 秒 CPU 的活，占用了 23.3 秒挂钟**，四分之三的时间在等文件读取。
对着 30 秒的挂钟预算，这是一个**做着 6 秒工作、却跑在自己上限 78% 位置**的门禁。

它已经翻过两次车，两次都紧跟在一次重量级 Gradle 之后（第一次 `clean test`，第二次下载
发行版并编译）——机器刚被塞了几千个新文件，Spotlight 开始建索引，读取变慢，
门禁于是"超时"。第一次原封不动重跑就变绿，看起来像偶发，其实是**裁决取决于机器当时在忙什么**。

这正是本仓库反复在处理的那类缺陷的镜像面。ADR-0013 记的是「门禁根本没跑起来」，
B09 记的是「门禁把坏输入变成崩溃等于放行」。这一条是：
**门禁跑不完和门禁判负，在退出码上长得一样，而 `exit 3` 在现场最常见的读法是「工具坏了，先跳过」。**
一个会因为别人在编译而变红的门禁，教会团队的第一件事就是重跑它；
教会的第二件事是不再相信它。

## 决策

`Budget` 同时持有两个数，任一超出都 fail closed：

1. **`seconds`（默认 30）现在计的是 `time.process_time()` 的增量**，即这次验证器运行
   实际消耗的进程 CPU 时间。它衡量的是**工作量**，与机器当时是否繁忙无关。
2. **`wall_ceiling`（默认 `seconds × 10`，即 300 秒）计挂钟**，作为兜底上限。

CPU 预算不会因为等待而消耗，所以它不再因为磁盘慢而误判；挂钟上限则保留了 B00 当初
真正要防的那件事——**一个不花 CPU 却迟迟不返回的验证器不是在工作，是卡住了**，
比如挂在一个停摆的挂载点或一个恶意 FIFO 上。CPU 时间单独一个数抓不到这种情况，
所以两个数都要。

倍数取 10 而不是 2：兜底上限只该在"明显不对劲"时触发。定得太近，
它就变成了刚被移除的那个挂钟预算，只是数字大一点。

`--budget-seconds` 的语义随之变成 CPU 秒。**`--budget-seconds 0` 仍然立即失败**，
各批次证据里那条「耗尽预算必须退 3，绝不退 0」的命令因此保持有效——这一点是刻意保住的，
它是整套 fail-closed 证明里最短也最重要的一条。

## 后果

- **`repo-hygiene` 的余量从 1.29 倍变成 5.1 倍**（5.9 秒 CPU 对 30 秒 CPU 预算），
  且不再随机器负载摆动。
- 负向控制harness（一次跑上百遍完整门禁、8 路并行）不再自己制造超时：
  并行竞争消耗的是挂钟，不是 CPU。
- **仓库继续长大仍然会消耗预算**，只是消耗的是真实工作量。CPU 时间超过 30 秒
  意味着门禁真的变慢了，那是该优化的信号，不是该调大的数字。
- `time.process_time()` **不含子进程**。当前没有验证器 fork 子进程；将来若有，
  它的 CPU 不计入，但仍受挂钟上限约束。这是一个已知的、有界的缺口，记在这里而不是留给下一个人发现。
- 这是 B00 产物 `tools/paygov/repo.py` 的改动，会改变 B00 的产物摘要，
  按既有规则需要重新基线——重签链本来就因为并发提交处于作废状态，此处不额外增加代价。

## 备选方案

1. **把挂钟预算调大到 120 秒。** 最省事，也最没意思：它把"门禁能否完成"继续绑在机器
   当时的负载上，只是把翻车点往后推。仓库还会长大，Spotlight 还会索引，
   这个数还得再调一次——而每调一次，这条规则就更像一个可以商量的数字。
2. **让 hygiene 更快（预编译正则 / 全文预筛）。** 我实测过：预筛能把 12 万行的扫描
   从 1.42 秒降到 1.01 秒，**1.4 倍**。CPU 本来就不是瓶颈，优化 CPU 解决不了一个等 I/O 的问题。
   （这个优化本身是无害的，但它不该被当成这条缺陷的修复而让人以为问题解决了。）
3. **并行读取文件。** 能压低挂钟，但把一个确定性的门禁变成一个受调度影响的门禁，
   与本 ADR 想要的性质正好相反。
4. **取消预算，只靠 CI 超时。** 那就把 fail-closed 从门禁里搬到了流水线配置里，
   而流水线配置不在 `verify-all` 的管辖范围内——NN-12 要求的是门禁自己 fail closed。

## 验证

- `Budget` 的五条行为由单元测试钉住：零预算立即失败；纯等待不消耗预算；
  真实 CPU 工作会消耗预算；不花 CPU 的停滞仍被挂钟上限抓住；默认上限为预算的 10 倍。
- 各批次证据中的「耗尽预算必须退 3」命令（`--budget-seconds 0`）继续通过。
- `verify-all` 在交付机上退 0，且 `repo-hygiene` 的 CPU 用量记录在批次证据的
  `runtime/` 目录里，使"门禁变慢了"成为可观测的事实而不是偶发故障。
