# ADR-0013: 治理工具链的解释器地板固定为 Python 3.10

- 状态：accepted
- 日期：2026-08-20
- 批次：B03
- 决策者：payment-platform-platform-eng payment-platform-architecture
- 关联需求：PAY-REQ-0049
- 关联控制：NN-12, CTRL-011, CTRL-018
- 取代：无

## 背景

ADR-0012 把 JDK、Gradle、Node、PostgreSQL 乃至渠道模拟器的 Python 都纳入了版本目录，
唯独漏掉了**跑这套治理工具链本身的解释器**。ADR-0010 规定治理工具链零第三方依赖，
于是「Python 版本」就是它唯一的运行时依赖——却是唯一没有所有者、没有升级策略、
没人固定的一个。

后果在 2026-08-20 兑现：两个执行环境分别是 Python 3.10.12 与 3.14，一段使用
`datetime.UTC`（3.11 才有的别名）的代码在较新的环境上写成并通过，落到较旧的环境上
则在 import 阶段就把整个 validator 注册表带崩——`verify-all` 抛出 traceback 而不是
给出裁决，4 个测试模块无法导入。**门禁不是判负，而是根本没跑起来**，这比判负更危险：
一个不会运行的门禁，和一个恒真的门禁，对交付的意义是一样的。

## 决策

版本目录新增 `python-toolchain` 条目，同时声明两个数：

1. `version`（精确固定，当前 3.12.7）——产出证据的**参考解释器**，与渠道模拟器同版本，
   全平台只维护一个 Python；
2. `minimum_supported`（当前 `3.10`）——**兼容地板**：工具链源码不得使用高于该地板的
   语法或标准库符号。

地板取 3.10 而非更高，理由是它必须等于**交付路径上仍在产出证据的最旧解释器**。把地板
抬到 3.12 在纸面上更干净，实际效果是把一个正在跑证据命令的环境判为不合规，而那个环境
不会因此消失，只会继续产出没人校验的证据。地板是事实描述，不是愿望。

`above_floor_symbols` 在目录中显式登记高于地板的标准库符号及其引入版本，作为规则的
数据源，而不是硬编码在校验器里。

## 后果

- 抬高地板需要新 ADR，因为它会把仍在产出证据的执行环境挡在门外；
- 工具链代码要放弃 3.11+ 的便利写法（`datetime.UTC`、`tomllib`、`typing.Self` 等），
  代价是少数几处更啰嗦的等价写法，`timezone.utc` 就是其中之一；
- `above_floor_symbols` 是一份人工维护的清单，天然不完备。它覆盖的是已知会在 import
  期炸掉的那一类符号；语法层面的越界由按地板版本解析源码来兜底。两者都不能替代在地板
  环境上真实跑一遍——所以地板环境仍然是交付路径的一部分，不是可选的。

## 备选方案

（a）只在 CI 固定解释器：拒绝。问题恰恰发生在 CI 之外的执行环境上，而证据正是在那里产出的；
（b）把地板抬到 3.12 并要求所有环境升级：拒绝。本会话无法在桥接工作区安装解释器，
   宣布一个做不到的要求等于把违规常态化；
（c）只做代码评审约定、不进门禁：拒绝。这次的越界正是评审没拦住的，而且它在较新的
   解释器上完全无症状——靠人眼发现「这个符号在旧版本没有」不可靠；
（d）用 `sys.version_info` 在运行时兜底降级：拒绝。它把版本差异变成分支逻辑，
   等于让工具链在不同环境上跑不同代码，与可重复构建的前提冲突。

## 验证

`tools/paygov/toolchain.py` 的 `TOOLCHAIN_INTERPRETER` 与 `TOOLCHAIN_PYTHON_FLOOR`：
目录缺条目、缺地板、地板高于参考版本、`above_floor_symbols` 为空或塞入并不高于地板的
符号、门禁运行在低于地板的解释器上，以及任一工具链源码使用越界符号或越界语法，
都会使门禁失败。符号匹配走语法树而非字符串包含，散文与同名标识符不会误报——
一条会误报的规则只会教人绕开它。`tools/tests/test_b03_toolchain.py::ToolchainInterpreter`
覆盖上述每一条，其中一项直接重放 2026-08-20 的原始回归；
`tools/negative/core.py` 的两个场景在完整门禁上验证退出码与规则代码；
两条规则均通过删除淘汰验证。
