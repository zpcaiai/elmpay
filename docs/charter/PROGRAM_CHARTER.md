## 1. 业务边界

### 1.1 平台拥有

- Payment Intent、Payment Attempt 与渠道交易事实。
- 渠道交互记录：请求、响应、回调原文、验签结果、主动查询结果。
- 退款、争议、订阅计费的支付侧事实。
- 复式账本、手续费/汇率/结算视图。
- 渠道账单、银行文件与三方对账结果。
- 风控信号、决策与案件证据。
- 商户/租户/项目注册、渠道账户绑定与路由配置。

### 1.2 平台不拥有

- 商品、库存、价格目录、促销与履约。
- 业务订单主数据与订单状态机。
- 用户账户体系与业务权限模型。
- 发票开具、税务申报与业务对客服务流程。

业务系统创建业务订单后，只向平台创建 Payment Intent，并以 `external_reference`
（项目 ID + 业务订单号）与支付事实关联。平台通过签名 Webhook 把支付事实推回业务系统。

### 1.3 明确排除的受监管能力

平台**不提供**自有余额、储值、资金池、跨商户清分与无牌代收代付。结算由持牌机构
直达商户结算账户。任何要求变更此边界的需求必须先取得牌照与法律意见，并新建独立
的合规评审批次；不得通过配置开关绕过。

## 2. 交付目标

| 目标 | 衡量方式 |
| --- | --- |
| G1 多项目统一接入 | 至少 3 个业务项目通过同一套 API/SDK 接入，业务订单不迁移 |
| G2 优先渠道打通 | 微信支付 APIv3、支付宝证书模式全模式沙箱认证通过（B40–B47、B55） |
| G3 国际渠道覆盖 | Stripe、PayPal、Apple Pay 沙箱认证通过（B48–B55） |
| G4 资金可解释 | 每一笔支付/退款可追溯到复式账本分录并与渠道账单、银行到账三方对账（B72–B79） |
| G5 风险可控 | 实时风控、反钓鱼、E-skimming、滥用防护上线并有攻击场景证据（B80–B87） |
| G6 可运营 | SLO、告警、运行手册、事件响应与日终对账（B96–B103、B125） |
| G7 可认证 | B00–B127 全部证据有效，RG0–RG7 全部通过（B127） |

## 3. 默认部署模式

- 单仓多模块（monorepo），按 `architecture/PROJECT_LAYOUT.md` 划分部署单元。
- 早期允许 `payment-core`、`merchant-config`、`risk-engine`、`ledger-service` 合并部署，
  但表所有权、事件边界与依赖方向从第一天起保持可拆分（见 `governance/module-registry.json`）。
- 运行时：Kubernetes + GitOps；数据面 PostgreSQL（事实源）、Kafka（可重放事件）、
  Redis（仅限流与可丢失缓存）。
- 主区域 `cn-east`；数据驻留 CN、EU 分区隔离（B94）。
- 卡数据范围：仅托管字段与 PSP 令牌，默认不落 CDE；Apple Pay token 直交 PSP。

## 4. 风险接受原则

1. **正确性优先于成功率与延迟。** 不得以放松验签、绕过 SCA、扩大卡数据范围、
   减少审计或关闭风控换取支付成功率。
2. **Fail closed。** 证据缺失、状态不确定、签名不可验证、账本不平时一律拒绝或挂起，
   不得默认放行。
3. **风险必须有主人。** 每条剩余风险登记风险所有者、补偿控制、到期日与复审批次。
4. **例外有期限。** 安全例外最长 90 天，到期自动阻断发布，需重新评审。
5. **不可逆动作双人。** 生产凭证、路由、密钥、退款阈值、人工账本调整、Webhook 回放
   与发布均需职责分离的四眼复核。
6. **风险接受权限分级。** 低风险由模块负责人接受；中风险由架构 + 安全共同接受；
   高风险必须由安全、财务、运维、产品四方签署（B119、B127）。

## 5. 不可绕过的安全红线

红线的机器可读形式为 `governance/non-negotiables.json`，与
`.payment-platform/skill-package/policies/non-negotiables.md` 保持 1:1 映射，
由 `tools/paygov` 在每次校验中强制执行。

| ID | 红线 |
| --- | --- |
| NN-01 | 业务订单不迁入支付中台 |
| NN-02 | 不托管原始卡数据（PAN/CVV/磁道/PIN） |
| NN-03 | 不以客户端成功为准 |
| NN-04 | 所有副作用幂等 |
| NN-05 | 金额使用最小单位整数 |
| NN-06 | 账本不可修改，只能反向或调整分录 |
| NN-07 | 密钥不落地，由 KMS/HSM/Vault 管理 |
| NN-08 | 回调先验签再持久化处理 |
| NN-09 | 严格租户隔离 |
| NN-10 | 禁止开放重定向 |
| NN-11 | 高风险操作四眼复核 |
| NN-12 | 证据不足即失败 |
| NN-13 | 不做无牌资金中介 |
| NN-14 | 日志最少化 |
| NN-15 | 安全例外有期限 |

违反任一红线的变更必须被 CI 阻断，不接受“临时豁免”“上线后补齐”“基本完成”。

## 6. 治理与批次门禁

- 推进顺序由 `.payment-platform/skill-package/manifest.json` 的依赖 DAG 决定，
  `scripts/orchestrate.py` 依据**真实证据**计算 ready，不依据文字声明。
- 每批次交付：代码/配置、契约或架构文档、自动化测试结果、安全与运行证据、
  `traceability.json`、`evidence/completion/Bxx.json`。
- 审查者不得是该批次唯一实现者。
- 本项目当前执行者为 `claude-agent`，独立审查者为 `Ethan`（见 `governance/project-config.json`）。

## 7. 变更控制

本章程的任何修改都是 ADR 级变更：必须新增 `docs/adr/` 记录、更新受影响批次证据，
并由架构与安全双方复核。章程版本号采用语义化版本。
